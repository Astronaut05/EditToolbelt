# 04 — Data model

Postgres, Drizzle ORM, migrations in `packages/db/migrations`. The database holds accounts, money, and job metadata. **Never** user files, filenames, or file contents.

Conventions: `id` is UUIDv7 (time-sortable) unless noted, with Postgres 18's native `uuidv7()` as the column default (decided 2026-09-29); `created_at`/`updated_at` `timestamptz` default `now()`; money in integer minor units; credits in integers.

### Money

**credit_transactions** — append-only ledger. No UPDATE or DELETE ever (enforced by a trigger that raises).
| column | type | notes |
|---|---|---|
| id | uuid pk | |
| user_id | fk users | |
| kind | enum | `purchase`, `welcome_grant`, `admin_grant`, `reserve`, `capture`, `release`, `refund_purchase`, `admin_debit` |
| amount | int | positive adds to balance, negative removes. `reserve` is negative, `release` positive, `capture` is 0-amount marker (the reserve already moved the balance) |
| job_id | uuid null, **no foreign key** | for reserve/capture/release. Indexed. No FK because job rows are deleted after 90 days and ledger rows can never be updated to drop the reference |
| purchase_id | fk purchases null | |
| admin_id | fk users null | who did an admin grant/debit |
| reason | text null | required for admin kinds |
| balance_after | int | running balance for auditing |

Invariant: `users.credit_balance = SUM(credit_transactions.amount)` for that user. Every write goes through one function `applyCredit(tx, userId, kind, amount, refs)` which inserts the row and updates the cached balance in the same transaction with `SELECT … FOR UPDATE` on the user row. A nightly job verifies the invariant for all users and alerts on any mismatch.

## Account deletion

User can delete their account from settings: sets `deleted_at`, revokes sessions and API keys, cancels queued jobs (releasing credits). After 30 days a job **scrubs the user row into a tombstone**: `email`, `display_name` and `locale` are nulled; Better Auth sessions/accounts/verifications and API keys are hard-deleted. The row's random `id` stays, so the append-only ledger and `purchases` keep valid references **without any UPDATE on `credit_transactions`** (the no-update trigger forbids it; re-pointing `user_id` to a shared tombstone id would have tripped it). With the email gone, the id no longer identifies anyone. Purchase records are kept for the legal retention period for tax/accounting, without email. Signing in during the 30-day grace restores the account; the same email can register a fresh account only after the scrub. Unused credits on deletion: stated in Terms (refund request window before deletion).
