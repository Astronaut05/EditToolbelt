# 2026-10-02 · A server job reads its input only as far as it was priced

**Decision:** `JobContext.run` gives every ffmpeg read of the job's input an input `-t` of the probed length × 1.02 + 1 s (`cap_input`, `priced_seconds` in `apps/worker/src/etb_worker/processors/__init__.py`). A shorter `-t` or `-to` that a processor set on that input is kept. A file that is longer than its header says is cut at the priced length and finishes normally; it is not refused.
**Why:** the review of Wave 3 and Noise Reduction found that the probe takes the length from the container header (`format.duration`), which the uploader writes, while the processors decoded the whole file. An MKV with its Segment Duration rewritten to 3 s was priced, limited and (for Noise Reduction) previewed for free as 3 s, then processed for 12 s. The same header got past the free tier's length limit. Capping in the one place every CPU processor runs ffmpeg covers today's tools (Compress Video, VFR to CFR, Burn Subtitles) and every later one without each remembering. An honest file never reaches the cap: streams run past the container's length by an audio frame or a last frame, not by 2 % plus a second. Cutting instead of refusing keeps one code path and gives the uploader what they paid for. The GPU functions get the same cap in their own decode (`claude/fix-gpu-decode-cap`).
**Reverse:** drop the `cap_input` call from `JobContext.run`. `tests/test_decode_cap.py` shows what comes back then: a 12 s result for a file priced as 3 s.
