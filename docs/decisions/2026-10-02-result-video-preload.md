# 2026-10-02 · A result's video player loads only its header until played, too

**Decision:** the shell's result `<video>` has `preload="metadata"`, like the result `<audio>` (the entry above). Before play it reads the header and decodes the first frame, which it shows; the rest loads on play. `rotate-resize-video.spec.ts` checks the attribute.
**Why:** Resize Video's framing test failed in WebKit on PR #67's CI (run 36996594698, job 110804626313): Download stayed off for 120 s. Playwright's check got only 16 answers, about 14 s' worth, which is when the crop ends and the shell commits the result with its player; then the page stopped answering, as with Merge Audio's freeze right after the result `<audio>`'s `loadstart`. Debug runs with stage logs and a 250 ms page heartbeat (37008253911, 37009439640, 37010634676) didn't bring the freeze back in 50 runs of the test, but showed Linux WebKit's media backend (GStreamer) failing on these results with the default preload (auto): 58 of 100 cropped WebM results ended in `MEDIA_ERR_SRC_NOT_SUPPORTED` without showing anything. With `metadata`, none of 100 failed and all reached `loadeddata`. Chromium's default is already `metadata`, and its first frame shows before play with the attribute or without (checked locally, desktop and phone). With the fix, both specs passed 8 times each in WebKit, 64 of 64 (37010972469).
**Reverse:** drop `preload` from the result `<video>` in `ToolShell.tsx` and the `toHaveAttribute('preload', 'metadata')` check in `rotate-resize-video.spec.ts`.
